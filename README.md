# Маршрут — прототип сервиса с планом продвижения

Веб-приложение, которое по короткой анкете собирает для владельца малого/среднего
бизнеса персональный пошаговый план продвижения и привлечения клиентов из интернета.
Инструкция формируется **не через ИИ**, а через движок правил, который комбинирует
готовые экспертные модули в зависимости от ответов — это предсказуемо, дёшево в
эксплуатации и легко улучшать вручную.

## Админ-панель — `/admin`

Отдельная страница для владельца сервиса, не привязанная к общей навигации
(ссылки на неё нет ни в шапке, ни в футере — только прямой переход по адресу).

**Что здесь по-настоящему работает:**

- **Вход по паролю** — теперь настоящая серверная проверка (`app/api/admin/login`),
  сверяет пароль с переменной окружения `ADMIN_PASSWORD` на сервере и ставит
  httpOnly-куку с HMAC-подписью (`lib/adminAuth.ts`, подписывается тем же
  `NEXTAUTH_SECRET`). В коде фронтенда пароль теперь не хранится и не виден в
  исходниках страницы
- **Вкладка «Пользователи»** — показывает реальных зарегистрированных людей из
  базы данных (`app/api/admin/users`), с фильтром по тарифу и удалением
  аккаунта (каскадно удаляет подписку, платежи и т.д. через Prisma)
- **Вкладка «Модули плана»** — реально управляет содержимым, которое получают
  пользователи. Можно отредактировать текст любого встроенного пункта
  (название, объяснение «почему это важно», шаги, срок до результата) и
  сбросить его к исходному варианту; можно добавить полностью новый пункт с
  собственным приоритетом и списком типов бизнеса, для которых он показывается.
  Формулу скоринга у встроенных пунктов через форму не поменять осознанно — это
  сложная логика в коде (`lib/modules.ts`), которую нельзя надёжно свести к
  простой форме, не потеряв в качестве рекомендаций; для новых пунктов вместо
  этого используется простое правило «приоритет + список типов бизнеса»
- **Вкладка «Сообщения»** — реально сохраняет переписку. Пользователь пишет в
  поддержку из личного кабинета → сообщение действительно появляется в этой
  вкладке; ответ администратора действительно появляется в личном кабинете
  пользователя. Ограничение то же, что и у остальных данных: это работает,
  только если пользователь и админ находятся в одном браузере (например, вы
  тестируете сами себя) — для доставки сообщений реальным людям на их
  устройства нужен бэкенд, который будет хранить переписку на сервере, а не
  в `localStorage` (`lib/support.ts` — на что заменить при переходе на бэкенд)

## ⚠️ Отдельно про политику персональных данных

Страница `/privacy` заявляет, что данные пользователей хранятся на серверах
на территории России и не передаются третьим лицам. **Прямо сейчас это не
факт, а описание целевой архитектуры**: в этом прототипе нет вообще никакого
сервера — все данные (email, профиль, подписка, сообщения) физически лежат в
`localStorage` браузера каждого посетителя, и никуда с его устройства не
уходят просто потому, что отправлять их некуда.

Это значит: пока вы не разверните настоящий бэкенд с базой данных на
российском хостинге (см. рекомендации в разделе про 152-ФЗ ниже) и не
подключите к нему Сервис, публиковать эту страницу как достоверное
юридическое заявление о том, где хранятся данные, нельзя — формально это
будет недостоверная информация, что уже вопрос не UX, а закона. Как только
бэкенд появится и данные пользователей реально переедут на сервер в РФ — текст
страницы сразу станет фактически верным, менять в нём ничего не придётся.

## Что уже готово в этом прототипе

- **Вектор аудитории** (только тарифы «Бизнес» и «Команда»): мини-квиз из 3
  вопросов после генерации плана определяет один из 9 психологических
  архетипов вашей аудитории (`lib/vectors.ts`) — боль, мечта, тон коммуникации
  и конкретные рекомендации по рекламе под этот тип клиентов. На тарифах без
  доступа — карточка с апселлом на тарифы. **Важно:** механика (архетипы
  аудитории + рекомендации под них) — общепринятый в маркетинге приём, но
  формулировки для профилей и вопросов квиза написаны заново, а не скопированы
  из присланных учебных материалов — те явно являются чужим платным курсом
  (подпись «by serge_ai» на каждом слайде), и встраивать их дословный текст в
  коммерческий продукт было бы юридически рискованно без прав от автора

- Удаление аккаунта — по-настоящему удаляет пользователя из базы данных
  (каскадно: подписку, платежи), доступно и из личного кабинета самим
  пользователем (`DELETE /api/me`), и из админки владельцем сервиса
  (`DELETE /api/admin/users/[id]`). Список бизнесов и переписка с поддержкой
  в этом браузере при этом тоже стираются, но они пока отдельно от БД (см.
  раздел про продакшен ниже)
- К сообщениям в техподдержке (и в ЛК, и в админке) можно приложить картинку:
  сжимается на клиенте до ≤1200px и сохраняется как часть сообщения
  (`lib/imageUtils.ts`, `components/ImageAttachField.tsx`) — реально работает
  в пределах одного браузера, как и вся система сообщений

- Политика обработки персональных данных (`/privacy`) — заявляет хранение
  данных на серверах в РФ и запрет передачи третьим лицам (кроме платёжной
  системы для проведения оплаты и случаев по закону). С тех пор как аккаунт и
  подписка переехали на PostgreSQL от Timeweb Cloud (дата-центр в РФ), это
  уже не только целевая архитектура, а факт — при условии, что вы
  задеплоили именно так, как описано в разделе про продакшен ниже
- Попап согласия перед оформлением любого тарифа теперь требует согласия сразу
  с договором оферты и с политикой персональных данных (два отдельных линка,
  одна галочка)
- Двусторонние сообщения между личным кабинетом и админкой (`lib/support.ts`):
  пользователь пишет в поддержку из ЛК → сообщение реально появляется во
  вкладке «Сообщения» в админке; админ может ответить или написать
  пользователю первым, выбрав его из таблицы пользователей. Работает только
  в пределах одного браузера — подробности в разделе про админ-панель

- Логотип «Ключевое слово» подключён из присланного файла: компактная марка
  на мобильных (`public/logo-mark.png`), полный лого-блок с подписью
  «Маркетинговое агентство» от планшетов и выше (`public/logo-full.png`), и
  фавикон вкладки браузера (`app/icon.png`), автоматически нарезанные из
  исходного файла
- Договор публичной оферты (`/oferta`) с реквизитами ИП и разделом, ещё раз
  закрепляющим информационный/рекомендательный характер сервиса (раздел 4) —
  текст один и тот же в `lib/offer.ts`, ссылки на него из футера, из блока
  «Ограничение ответственности» и из попапа согласия при оформлении тарифа
- Лендинг с объяснением продукта
- Анкета из 7 вопросов (мастер по шагам)
- Движок правил (`lib/ruleEngine.ts`), который на основе ответов собирает план из
  11 модулей (`lib/modules.ts`), сгруппированный в 3 этапа: фундамент → трафик →
  удержание клиентов
- UI результата: раскрывающиеся карточки с шагами, объяснением «почему именно это»
  и ориентиром по срокам
- Секция кейсов — 6 карточек в горизонтальном слайдере со стрелками прокрутки
  (свайп на мобильных работает нативно через скролл)
- Секция тарифов (4 плана, включая бесплатный пробный) — оплата платных
  тарифов реальная, через ЮKassa (см. раздел про продакшен ниже)
- Форма заявки «Если остались вопросы» под тарифами — сейчас ничего никуда не
  отправляет, только показывает подтверждение на экране (см. следующий раздел)
- Блок «Ограничение ответственности» на странице и попап с этим же текстом и
  чекбоксом согласия перед оформлением любого тарифа — кнопка «Оформить
  подписку» внутри попапа неактивна, пока не поставлена галочка
  (`lib/disclaimer.ts` — единый источник текста для обоих мест)
- Мобильная адаптация: шапка с иконкой личного кабинета вместо текстовой
  ссылки на узких экранах, полноширинные кнопки и перенос строк в плотных
  местах интерфейса, уменьшенные отступы и размер заголовка хиро на самых
  маленьких экранах (проверено от ~320px)
- В личном кабинете видна дата окончания оплаченного периода. При отмене
  автопродления доступ к тарифу сохраняется до конца уже оплаченного периода
  (30 дней от активации), дальше аккаунт автоматически откатывается на тариф
  «Пробный» — это учитывает и анкета (лимит бизнесов и видимость этапов)
- Обязательная регистрация по email и паролю перед стартом анкеты — реальная,
  через NextAuth и PostgreSQL (`app/api/register`, `lib/auth.ts`), а не мок
- Ограничение пробного тарифа: после анкеты видно только 2 из 3 этапов плана,
  третий — заблокирован с призывом оформить подписку. На тарифах «Старт»,
  «Бизнес» и «Команда» видны все 3 этапа (`lib/plans.ts`, поле `fullPlanAccess`)
- Кнопка «Скачать PDF» — генерирует настоящий PDF на сервере (`lib/pdfGenerator.ts`,
  через `pdf-lib`) и сразу скачивает его. Кириллица печатается корректно за
  счёт встроенного в PDF шрифта (`lib/fonts/NotoSans-*.ttf`) — обычные JS-PDF
  библиотеки вроде jsPDF без этого шрифт не умеют
- Кнопка «Получить PDF на почту» — реально формирует тот же PDF и отправляет
  его вложением на email пользователя через уже настроенный SMTP
  (`app/api/plan/email-pdf`). Какие этапы попадают в PDF — решает сервер по
  реальной подписке пользователя в базе, а не то, что прислал браузер — иначе
  можно было бы получить закрытый этап 3 в обход оплаты
- **Личный кабинет** (`/account`): данные профиля (имя, телефон), карточка
  подписки со статусом и кнопкой «Отменить/Возобновить подписку», список своих
  бизнесов с удалением
- **Лимит бизнесов по тарифу** (`lib/plans.ts` → `businessLimit`): «Пробный» и
  «Старт» — 1 бизнес, «Бизнес» — 3, «Команда» — 5. Перед анкетой сервис
  спрашивает название бизнеса и проверяет лимит; при превышении показывает
  экран с призывом освободить слот в личном кабинете или сменить тариф
- Нажатие «Оформить подписку» в прайсинге создаёт настоящий платёж в ЮKassa
  и редиректит на его оплату; после успешной оплаты вебхук ЮKassa активирует
  подписку в базе данных — подробности в разделе про продакшен ниже

## Чего пока нет (следующие шаги)

1. **Список бизнесов и сам сгенерированный план** — модель `Business` уже есть
   в `prisma/schema.prisma`, но пока не подключена: бизнесы по-прежнему в
   `localStorage`, а открыть повторно уже сгенерированный план нельзя, можно
   только создать новый (в рамках лимита тарифа). Подробности — в разделе про
   продакшен выше
2. **Обработка формы «Если остались вопросы»** — нужен серверный маршрут
   (`app/api/contact/route.ts`), который отправит заявку в Telegram-бот или на
   почту и сохранит её в базе, чтобы не терять обращения
3. **Хранение картинок из сообщений в localStorage — временное решение.**
   У браузеров есть лимит на объём localStorage (обычно 5–10МБ на сайт).
   Сжатие до 1200px по стороне сильно откладывает проблему, но не решает её
   полностью. В боевой версии картинки должны загружаться в файловое хранилище
   (например, Timeweb S3) и в сообщении храниться только ссылка на файл

## Запуск локально

Нужна доступная PostgreSQL (например, та же от Timeweb) и заполненный `.env`
— скопируйте `.env.example` и подставьте свои значения (подробнее — в
разделе про продакшен ниже).

```bash
cp .env.example .env    # и заполнить реальными значениями
npm install               # заодно сгенерирует Prisma Client (postinstall)
npx prisma migrate deploy   # создать таблицы в базе
npm run dev
```

Откройте http://localhost:3000

### Как добавить новый модуль в план

Откройте `lib/modules.ts` и добавьте объект в массив `MODULES`:

```ts
{
  id: "vk_market",
  title: "Название модуля",
  phase: "traffic", // foundation | traffic | retention
  minBudget: "20to100",
  timeToResult: "2-3 недели",
  why: (a) => `Текст объяснения, можно использовать ${a.businessType} и другие поля ответов`,
  steps: ["Шаг 1", "Шаг 2", "Шаг 3"],
  score: (a) => {
    // чем выше число, тем выше приоритет модуля в плане; 0 или отрицательное — модуль не покажется
    let s = 5;
    if (a.goal === "leads") s += 2;
    return s;
  },
},
```

Это единственное место, которое нужно трогать, чтобы расширять экспертизу продукта —
не нужно лезть в UI.

## Продакшен: база данных, оплата и деплой на Timeweb

Эта часть уже реализована по-настоящему (не мок): регистрация и вход через
пароль, подписка и платежи хранятся в PostgreSQL через Prisma, оплата — через
ЮKassa. Список бизнесов, переписка с поддержкой и правки модулей из админки
пока остаются на `localStorage` — это следующий шаг, ниже отдельно объясню
почему так и что делать дальше.

### Что нужно, чтобы это заработало

1. **PostgreSQL от Timeweb Cloud** — в панели: «Базы данных» → «Создать» →
   PostgreSQL. После создания скопируйте строку подключения — она пригодится
   для `DATABASE_URL`.
2. **Ключи ЮKassa** — в личном кабинете ЮKassa: «Настройки» → «API-ключи».
   Понадобятся `shopId` и «Секретный ключ» (не путать с ключом для виджета).
   Пока используйте тестовый магазин («Тестовый режим» в кабинете ЮKassa),
   чтобы прогнать оплату без реальных денег перед запуском на боевых ключах.
3. **Приложение на Timeweb Cloud App Platform** — «Apps» → «Создать» →
   подключить ваш GitHub-репозиторий → тип Next.js → **обязательно включить
   поддержку SSR** (без этого API-роуты работать не будут, а именно через них
   и работает оплата).

### Переменные окружения

Скопируйте `.env.example` в `.env` для локальной разработки, а в панели
Timeweb Cloud App Platform заполните те же переменные в разделе окружения
приложения:

```
DATABASE_URL=...        # из панели Timeweb → Базы данных → PostgreSQL
NEXTAUTH_SECRET=...      # openssl rand -base64 32
NEXTAUTH_URL=...          # https://ваш-домен, без / на конце
YOOKASSA_SHOP_ID=...
YOOKASSA_SECRET_KEY=...
ADMIN_PASSWORD=...          # см. предупреждение про /admin выше по тексту
CRON_SECRET=...               # придумайте случайную строку для защиты /api/cron/renew
```

### Применение схемы БД

После первого деплоя (или локально, указав `DATABASE_URL` от Timeweb) один раз:

```bash
npx prisma migrate deploy
```

Эта команда создаст все таблицы по `prisma/schema.prisma`. При последующих
изменениях схемы: `npx prisma migrate dev --name какое-то-имя` локально,
закоммитить файл миграции из `prisma/migrations/`, на проде — снова
`prisma migrate deploy`.

### Как настроен платёж технически

1. `PricingSection` → `POST /api/payments/create` создаёт платёж в ЮKassa
   через `lib/yookassa.ts` с `save_payment_method: true` (чтобы можно было
   списывать автоматически дальше) и редиректит пользователя на страницу
   оплаты ЮKassa
2. После оплаты ЮKassa стучится на `POST /api/payments/webhook` — этот адрес
   нужно вручную указать в личном кабинете ЮKassa: «Настройки» → «HTTP-уведомления»
   → `https://ваш-домен/api/payments/webhook`
3. Обработчик вебхука **не доверяет телу запроса** — по `payment.id` заново
   запрашивает статус напрямую у ЮKassa (`getYookassaPayment`) и только потом
   активирует подписку в базе. Это защита от поддельных POST-запросов на адрес
   вебхука
4. `POST /api/cron/renew` списывает деньги за следующий период сохранённым
   способом оплаты для подписок, у которых период заканчивается в течение
   суток. Сам роут ничего не продлевает — он только инициирует платёж, а
   продление даты происходит там же, где и для первой оплаты — в вебхуке,
   когда придёт подтверждение об успешном списании

**Этот роут нужно дёргать по расписанию** — Timeweb App Platform не имеет
встроенного cron для приложений, поэтому варианты: внешний сервис вроде
cron-job.org, который раз в день делает `POST` на
`https://ваш-домен/api/cron/renew` с заголовком `x-cron-secret: ваш CRON_SECRET`,
либо отдельный VPS/сервер с обычным `crontab`, если он у вас уже есть.

### Локальная проверка перед деплоем

```bash
npm install
npx prisma generate
npm run build
```

Если что-то не собирается именно на строке с `@prisma/client` — почти всегда
причина в том, что `prisma generate` не был запущен (например, если
устанавливали зависимости в среде без доступа к `binaries.prisma.sh`).
`postinstall`-скрипт в `package.json` делает это автоматически при обычном
`npm install`, так что в норме это не должно требовать ручных действий.

### Почему бизнесы, сообщения и модули пока не в базе

Чтобы не переписывать весь прототип разом и не сломать то, что касается
реальных денег, в этот проход я перенёс в базу только то, что напрямую
завязано на оплату: аккаунт и подписку. Список бизнесов (`lib/account.ts`),
переписка с поддержкой (`lib/support.ts`) и правки модулей из админки
(`lib/adminModules.ts`) остаются на `localStorage` браузера — то есть
привязаны к устройству, а не к аккаунту в базе. Со стороны это не сломано —
всё продолжает работать так же, как раньше, — но это следующий логичный шаг:
перенести `Business` и `SupportMessage` (они уже есть в `prisma/schema.prisma`)
на реальные API-роуты по аналогии с `/api/me`.

### 152-ФЗ теперь закрыт по-настоящему

PostgreSQL от Timeweb Cloud физически расположен в дата-центре в России —
значит, в отличие от прежнего прототипа на `localStorage`, теперь
формулировка в `/privacy` про «серверы на территории РФ» соответствует
действительности, как только вы фактически задеплоите приложение с этой
базой данных.

## Аудит безопасности

Прошёлся по коду системно: авторизация, права доступа между пользователями,
обработка платежей, защита от перебора и подбора, стандартные заголовки.
Дата аудита стоит в истории коммитов — если пройдёт много времени, есть
смысл повторить хотя бы пункт про версию Next.js ниже.

### Что нашёл и исправил сразу

- **Устаревшая версия Next.js.** `npm audit` показал больше десятка известных
  уязвимостей в закреплённой версии 14.2.35, включая одну критическую (RCE
  через оптимизатор картинок при обработке AVIF-файлов). Проверил, какие из
  них реально касаются нашего кода: мы не используем middleware, i18n,
  Server Actions, WebSocket, `rewrites`, и не хостимся на Windows — это
  снимает большинство пунктов из списка. Единственное реально
  затрагивающее нас место — `next/image`, но он используется только для
  одного локального логотипа, без `remotePatterns` на внешние адреса. Тем не
  менее, отключил оптимизатор картинок совсем (`images.unoptimized: true` в
  `next.config.js`) — это разом убирает весь класс уязвимостей в этом узле
  без каких-либо рисков для функциональности (логотипу оптимизация и не
  нужна). **Саму версию Next.js это не чинит** — сборка теперь просто не
  использует уязвимый функционал. Полноценно закрыть вопрос может только
  обновление на Next.js 15 или 16 — это отдельная задача с тестированием,
  ниже она в списке следующих шагов
- **Не было лимита попыток входа и регистрации.** Пароль можно было
  перебирать сколько угодно раз подряд — ни на вход в аккаунт, ни на вход в
  админку, ни на регистрацию ограничений не было. Добавил простой лимитер
  (`lib/rateLimit.ts`, в памяти процесса): 10 попыток входа на email за
  15 минут, 10 попыток на вход в админку за 15 минут с одного IP, 5 попыток
  регистрации за 15 минут с одного IP. Это не защита промышленного уровня
  (не переживёт перезапуск контейнера, не будет работать при нескольких
  инстансах одновременно), но для одного контейнера — то что нужно уже
  сейчас, без внешних зависимостей вроде Redis
- **Сравнение пароля админки не было защищено от timing-атак.** Обычное
  `password !== expected` теоретически позволяет по времени ответа сервера
  угадывать пароль посимвольно. Заменил на `timingSafeEqual` — тот же
  принцип, что уже использовался для проверки сессии админки. То же самое
  поправил и для секрета cron-задачи
- **Адрес возврата после оплаты брался из заголовка `Origin`**, который
  клиент теоретически может подделать (не браузером, так скриптом). Заменил
  на собственный `NEXTAUTH_URL` — сервер больше не доверяет в этом месте
  ничему, что прислал клиент
- **Не было ограничений на размер данных плана**, которые клиент присылает
  при формировании PDF — теоретически можно было прислать огромный JSON и
  заставить сервер тратить ресурсы на генерацию гигантского файла. Добавил
  разумные пределы (`lib/planValidation.ts`): не больше 10 пунктов на этап,
  20 шагов на пункт, 2000 символов на текстовое поле
- **Не было лимитов на создание платежей, отправку PDF на почту и на
  вебхук** — тоже добавил (см. код соответствующих роутов), чтобы нельзя
  было заспамить ЮKassa API через наш сервер или завалить сервер потоком
  поддельных вебхуков
- **Не было стандартных заголовков безопасности** (`X-Frame-Options`,
  `X-Content-Type-Options` и т.д.) — добавил через `headers()` в
  `next.config.js`. `Content-Security-Policy` осознанно не добавлял: чтобы
  сделать её правильно (не сломав шрифты с Google Fonts и инлайн-стили
  Tailwind), нужно отдельно тестировать — не хотел добавлять её на скорую
  руку и случайно что-то сломать
- **`app/api/debug/smtp-test`** — диагностический роут, которым мы вместе
  находили причину проблем с почтой, уже удалён из кода раньше

### Что проверил и признал безопасным

- **IDOR (доступ к чужим данным).** Прошёлся по всем роутам — везде, где
  нужно, данные фильтруются по `user.id` из сессии, а не по тому, что
  прислал клиент. Админские роуты проверяют отдельную куку `admin_session`,
  не пересекаются с обычной пользовательской сессией
- **CSRF.** Все куки сессии (и NextAuth, и админки) стоят с `sameSite: lax`
  — браузеры не прикладывают такие куки к кросс-доменным POST/DELETE
  запросам с чужих сайтов, это стандартная защита без необходимости отдельно
  городить CSRF-токены
- **Вебхук ЮKassa.** Не доверяет статусу платежа из тела запроса — всегда
  перепроверяет напрямую через API ЮKassa по `payment.id`, поэтому
  подделать вебхук случайным POST-запросом нельзя
- **SQL-инъекции.** Весь доступ к базе — через Prisma с параметризованными
  запросами, сырых SQL-строк с конкатенацией пользовательского ввода в коде
  нет
- **Пароли пользователей** хранятся только как bcrypt-хеш, нигде в коде не
  логируются и не возвращаются в ответах API

### Что осталось как рекомендация на будущее (не блокирует запуск)

- Обновление Next.js до актуальной ветки (15.x или 16.x) — с тестированием,
  отдельной задачей
- `Content-Security-Policy` — после того, как заголовки будут протестированы
  вручную на проде
- Лимитер сейчас в памяти процесса — при росте до нескольких
  инстансов/подов стоит перейти на Redis или аналог
